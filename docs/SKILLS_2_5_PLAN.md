# План внедрения Skills 2.5 для 1С-агента

## Цель

Добавить в агента слой skills, который сначала работает как `Skill Registry + Selector`, но сразу хранит contract-ready поля для будущего строгого контроля DSL.

Подход 2.5:

- сейчас: выбирать релевантные skills и добавлять их инструкции в промпт;
- рядом: логировать выбор, версионировать skills, ограничивать бюджет контекста;
- позже: включить runtime enforcement для allowed actions, required checks, risk level и approval.

## Архитектурная идея

Текущий контур:

```text
Пользователь -> ИИА_Оркестратор -> ИИА_Промты -> LLM -> DSL -> ИИА_DSL -> 1С
```

Целевой контур:

```text
Пользователь
  -> ИИА_Skills.ПодобратьСкилы()
  -> ИИА_Промты + блок выбранных skills
  -> LLM
  -> DSL
  -> ИИА_DSL
  -> позже: ИИА_Skills.ВалидироватьDSLПоСкилам()
  -> 1С
```

## Формат skill

На первом этапе skill можно хранить в JSON-строке, макете, регистре сведений или общем модуле. Важно сразу заложить поля будущего контракта.

```json
{
  "name": "query-1c-safe",
  "version": 1,
  "description": "Построение безопасных запросов 1С с проверкой метаданных",
  "triggers": ["покажи", "выбери", "отчет", "остатки", "продажи"],
  "dialog_types": ["Агент", "Запрос1С"],
  "priority": 100,
  "enabled": true,
  "prompt": "Сначала используй RAG/GetMetadata/GetObjectFields для уточнения объектов и полей. Для дат используй ДАТАВРЕМЯ(...). Не используй ТекущаяДата(). Для пользовательского результата применяй ShowInfo.",
  "risk_level": "read",
  "allowed_actions": ["GetMetadata", "GetObjectFields", "CheckObjectExists", "RunQuery", "ShowInfo"],
  "forbidden_actions": ["CreateReference", "CreateDocument", "SetField", "Write"],
  "required_checks": ["metadata_before_query"],
  "approval_required": false,
  "max_prompt_chars": 1600,
  "enforcement": "off"
}
```

## Этап 1. Минимальный Skill Registry

Создать общий модуль `ИИА_Skills`.

Публичные функции:

- `ПолучитьРеестрСкилов() Экспорт`
- `ПолучитьАктивныеСкилы() Экспорт`
- `ПолучитьСкил(ИмяСкила) Экспорт`
- `СформироватьБлокСкилов(Скилы, МаксимумСимволов = 4000) Экспорт`

На MVP реестр можно держать в коде общего модуля, чтобы быстрее проверить эффект. После стабилизации перенести в регистр сведений.

## Этап 2. Skill Selector

Добавить функцию:

```bsl
Функция ПодобратьСкилы(ТекстПользователя, ТипДиалога, Контекст = Неопределено, Максимум = 3) Экспорт
```

Логика MVP:

- нормализовать текст пользователя в нижний регистр;
- отфильтровать skills по `enabled` и `dialog_types`;
- начислить score за совпадение `triggers`;
- добавить бонус за приоритет;
- вернуть top-N;
- если ничего не найдено, вернуть базовый skill `default-agent-behavior`.

Важно: selector должен быть детерминированным и дешёвым. LLM для выбора skill на первом этапе не нужен.

## Этап 3. Встраивание в промпты

В `ИИА_Промты.СформироватьПромпт()` добавить получение skill-блока рядом с RAG-контекстом.

Предлагаемый формат блока:

```text
АКТИВНЫЕ SKILLS:

[query-1c-safe v1]
Сначала используй RAG/GetMetadata/GetObjectFields...

[dsl-recovery v1]
Если RunQuery вернул ошибку...
```

Правила:

- добавлять только выбранные skills;
- ограничивать общий размер блока;
- не дублировать правила, которые уже есть в RAG;
- писать в лог, какие skills были добавлены.

## Этап 4. Логирование и наблюдаемость

Добавить записи в лог диалога:

```text
[SKILL_SELECTED] names=query-1c-safe,metadata-discovery reason=trigger_match score=...
[SKILL_PROMPT_ADDED] chars=2480 budget=4000
```

Минимальные поля:

- `names`
- `scores`
- `reason`
- `prompt_chars`
- `enforcement`
- `dialog_type`

Это нужно, чтобы сравнивать качество до/после и быстро видеть, почему агент выбрал конкретное поведение.

## Этап 5. Первый набор skills

### `query-1c-safe`

Для запросов чтения данных.

Триггеры:

- покажи
- выбери
- отчет
- продажи
- остатки
- топ
- список

Основные правила:

- сначала уточнять объекты и поля;
- использовать RAG как приоритетный источник имен;
- даты писать через `ДАТАВРЕМЯ`;
- не использовать `ТекущаяДата()`;
- ограничивать результат через `ПЕРВЫЕ`;
- результат показывать через `ShowInfo`.

### `metadata-discovery`

Для поиска объектов, полей и синонимов.

Основные правила:

- не запрашивать полный список метаданных без фильтра;
- при неудаче подбирать синонимы;
- после найденного объекта вызывать `GetObjectFields`;
- не возвращаться к уже отвергнутому имени объекта.

### `dsl-recovery`

Для исправления ошибок выполнения DSL.

Основные правила:

- не повторять тот же ошибочный DSL;
- если ошибка в поле, вызвать `GetObjectFields`;
- если ошибка в объекте, вызвать `GetMetadata` с альтернативными фильтрами;
- после успешной проверки перейти к `RunQuery`;
- не завершать задачу без попытки recovery.

### `create-reference-safe`

Для создания элементов справочников.

Основные правила:

- сначала проверить существование справочника;
- проверить поля;
- создать объект через `CreateReference`;
- заполнить поля через `SetField`;
- записать через `Write`;
- при неоднозначности запросить уточнение или approval.

### `document-workflow`

Для создания и изменения документов.

Основные правила:

- всегда считать workflow рискованным;
- перед записью или проведением требовать approval;
- проверять реквизиты и табличные части;
- не проводить документ без явной команды пользователя.

## Этап 6. Contract-ready поля без строгого enforcement

На первом релизе поля `allowed_actions`, `forbidden_actions`, `required_checks`, `risk_level`, `approval_required` только хранятся и логируются.

Режимы enforcement:

- `off` - только промпт и логирование;
- `warn` - валидатор пишет предупреждение, но не блокирует;
- `strict` - валидатор блокирует запрещённый DSL.

Для MVP использовать:

```json
"enforcement": "off"
```

## Этап 7. Warn-валидатор DSL

После стабилизации selector добавить:

```bsl
Функция ПроверитьDSLПоСкилам(DSLJSON, Скилы, Режим = "warn") Экспорт
```

Проверки:

- action отсутствует в `allowed_actions`;
- action входит в `forbidden_actions`;
- write-action используется при `risk_level = read`;
- required check не был выполнен перед risky action;
- для `approval_required = true` нет шага approval.

В режиме `warn` результат только логируется:

```text
[SKILL_POLICY_WARN] skill=query-1c-safe action=Write reason=forbidden_action
```

## Этап 8. Strict enforcement для рискованных skills

Включать `strict` постепенно:

1. `query-1c-safe` - запрет write-actions.
2. `document-workflow` - обязательный approval.
3. `create-reference-safe` - проверка обязательной цепочки `CheckObjectExists/GetObjectFields -> CreateReference -> SetField -> Write`.

При блокировке возвращать системный результат в формате DSL error, чтобы оркестратор мог восстановиться:

```json
{
  "kind": "dsl_system_result",
  "success": false,
  "error_code": "skill_policy_violation",
  "error": "Skill query-1c-safe запрещает действие Write",
  "details": {
    "skill": "query-1c-safe",
    "action": "Write"
  }
}
```

## Этап 9. Тестирование

Минимальные тесты:

- selector выбирает `query-1c-safe` для запроса "покажи продажи за месяц";
- selector выбирает `create-reference-safe` для "создай контрагента";
- selector выбирает `dsl-recovery` после ошибки RunQuery;
- skill-блок попадает в промпт и не превышает бюджет;
- warn-валидатор логирует запрещённый `Write` для read-skill;
- strict-валидатор блокирует запрещённый action.

Интеграционные сценарии:

- вопрос на чтение данных с RAG;
- запрос с неправильным названием объекта;
- ошибка поля в `RunQuery` и восстановление через `GetObjectFields`;
- создание элемента справочника с approval;
- попытка записи в режиме read-only.

## Этап 10. Критерии готовности MVP

MVP готов, если:

- есть `ИИА_Skills`;
- минимум 3 skills доступны в реестре;
- selector выбирает skills без LLM;
- выбранные skills добавляются в промпт;
- выбор skills логируется;
- общий размер skill-блока ограничен;
- текущие сценарии агента не сломаны;
- есть хотя бы базовые тесты selector и prompt injection.

## Этап 11. Пользовательское управление skills

Пользователь не должен редактировать JSON напрямую. JSON/contract-ready структура остается внутренним форматом, а в 1С нужна форма управления skills.

Рекомендуемый интерфейс:

```text
ИИ-Агент -> Настройки -> Skills
```

Список skills:

```text
[✓] Создание заказа клиента
[✓] Анализ продаж
[ ] Массовое создание контрагентов
[✓] Проверка остатков перед продажей
```

Карточка skill:

```text
Название: Создание заказа клиента

Когда применять:
- создай заказ клиента
- оформи заказ
- клиент хочет купить
- сделай заказ на товары

Что должен делать агент:
1. Найти контрагента по наименованию.
2. Если не найден - предложить создать.
3. Создать документ ЗаказКлиента.
4. Заполнить организацию, контрагента, склад.
5. Добавить товары в табличную часть.
6. Проверить остатки.
7. Показать пользователю предварительный результат.
8. Записать документ только после подтверждения.
```

Ограничения в карточке:

```text
Разрешено:
[✓] Читать данные
[✓] Создавать документ
[✓] Заполнять поля
[✓] Записывать документ
[ ] Проводить документ

Требовать подтверждение:
[✓] Перед записью
[✓] Перед проведением
```

### Режимы создания skill пользователем

#### Простой режим

Пользователь описывает skill обычным текстом:

```text
Когда я прошу создать заказ клиента, найди клиента, создай заказ, добавь товары, проверь остатки и перед записью спроси подтверждение.
```

Агент формирует черновик skill:

- название;
- фразы-триггеры;
- целевой объект метаданных;
- шаги процесса;
- риски;
- необходимость подтверждения;
- разрешенные и запрещенные действия.

Пользователь проверяет черновик и сохраняет skill.

#### Мастер

Форма пошагово собирает описание:

```text
Как называется skill?
Когда его применять?
Какой объект создавать или изменять?
Какие поля заполнять?
Нужна ли запись?
Нужно ли проведение?
Когда спрашивать подтверждение?
Кому доступен skill?
```

Это основной безопасный режим для обычных пользователей.

#### Экспертный режим

Доступен администратору или разработчику.

Позволяет редактировать:

- prompt;
- triggers;
- allowed actions;
- forbidden actions;
- required checks;
- risk level;
- enforcement `off/warn/strict`.

### Пример пользовательского skill для создания документа

Пользователь говорит агенту:

```text
Создай скил: когда я пишу "оформи заявку на оплату", агент должен создать документ ЗаявкаНаРасходованиеДенежныхСредств, заполнить контрагента, сумму, статью ДДС, договор и показать перед записью.
```

Агент предлагает черновик:

```text
Skill: Оформление заявки на оплату

Будет применяться к фразам:
- оформи заявку на оплату
- создай заявку на расходование ДС
- подготовь платежную заявку

Действия:
1. Найти контрагента.
2. Найти договор.
3. Создать документ ЗаявкаНаРасходованиеДенежныхСредств.
4. Заполнить сумму, статью ДДС, договор.
5. Показать предварительный результат.
6. Записать только после подтверждения.

Запись в базу: только после подтверждения.
Проведение: запрещено.
```

Внутреннее представление:

```json
{
  "name": "user-create-payment-request",
  "title": "Оформление заявки на оплату",
  "owner": "user",
  "enabled": true,
  "triggers": ["оформи заявку на оплату", "создай заявку на расходование ДС", "подготовь платежную заявку"],
  "target_object": {
    "type": "Document",
    "name": "ЗаявкаНаРасходованиеДенежныхСредств"
  },
  "prompt": "Создавай документ ЗаявкаНаРасходованиеДенежныхСредств по процедуре пользователя. Перед записью показывай предварительный результат и запрашивай подтверждение.",
  "workflow": [
    "Найти контрагента",
    "Найти договор",
    "Создать документ",
    "Заполнить сумму, статью ДДС и договор",
    "Показать preview",
    "Записать после подтверждения"
  ],
  "template_vars": {
    "customer": {
      "type": "CatalogRef.Контрагенты",
      "required": true,
      "source": "user_prompt"
    },
    "amount": {
      "type": "number",
      "required": true,
      "source": "user_prompt"
    },
    "target_object": {
      "type": "Document.ЗаявкаНаРасходованиеДенежныхСредств",
      "required": true,
      "source": "skill"
    }
  },
  "dsl_template_mode": "validate",
  "dsl_template": {
    "dsl_version": 1,
    "steps": [
      {"action": "GetMetadata", "object": "Document.ЗаявкаНаРасходованиеДенежныхСредств", "save_as": "metadata"},
      {"action": "FindReferenceByName", "object": "Catalog.Контрагенты", "value": "$customer", "save_as": "customer_ref"},
      {"action": "CreateDocument", "object": "ЗаявкаНаРасходованиеДенежныхСредств", "save_as": "document_ref"},
      {"action": "SetField", "target": "$document_ref", "field": "Контрагент", "value": "$customer_ref"},
      {"action": "SetField", "target": "$document_ref", "field": "СуммаДокумента", "value": "$amount"},
      {"action": "ShowInfo", "value": "Предварительный результат подготовлен. Запись только после подтверждения пользователя."}
    ]
  },
  "allowed_actions": ["GetMetadata", "GetObjectFields", "FindReferenceByName", "CreateDocument", "SetField", "Write", "RunQuery", "ShowInfo"],
  "forbidden_actions": ["PostDocument", "DeleteObject"],
  "required_checks": ["metadata_before_write", "approval_before_write"],
  "approval_required": true,
  "risk_level": "write",
  "enforcement": "warn"
}
```

### Область видимости и права

У каждого пользовательского skill должна быть область видимости:

```text
Доступен:
( ) Только мне
( ) Моей группе
( ) Всем пользователям
```

Права:

- владелец может редактировать личный skill;
- администратор может редактировать все skills;
- публикация skill для всех пользователей требует прав администратора;
- перевод `enforcement` в `strict` требует прав администратора.

### Безопасные настройки по умолчанию

Новый пользовательский skill должен создаваться так:

- `enabled = false` до подтверждения пользователем;
- `enforcement = "warn"`;
- `approval_required = true` для любых write-actions;
- проведение документов запрещено по умолчанию;
- удаление объектов запрещено всегда, пока нет отдельной политики;
- произвольный код 1С запрещен;
- skill может использовать только разрешенные DSL actions.

### Хранение пользовательских skills

Для MVP можно использовать регистр сведений `ИИА_Скилы`.

Поля:

- `Имя`
- `Заголовок`
- `Описание`
- `Владелец`
- `ОбластьВидимости`
- `Активен`
- `Версия`
- `Триггеры`
- `ТипыДиалогов`
- `ЦелевойОбъектТип`
- `ЦелевойОбъектИмя`
- `Инструкция`
- `WorkflowJSON`
- `PolicyJSON`
- `TemplateVarsJSON`
- `DSLTemplateJSON`
- `DSLTemplateMode`
- `Enforcement`
- `ДатаСоздания`
- `ДатаИзменения`

На уровне `ИИА_Skills.ПолучитьРеестрСкилов()` нужно объединять:

- системные skills из кода или поставки;
- пользовательские skills из регистра;
- отключенные или недоступные по правам skills отфильтровывать.

`workflow` остается человекочитаемым сценарием для пользователя/разработчика, а `dsl_template` - машинным каркасом для агента. Режимы шаблона:

- `hint` - использовать как подсказку, можно адаптировать свободно;
- `validate` - использовать как проверяемый каркас, адаптируя значения и безопасные уточняющие шаги;
- `strict` - строить DSL строго по шаблону, отклонения должны быть явно обоснованы и дополнительно проверены.

### Жизненный цикл пользовательского skill

```text
Черновик -> Проверен пользователем -> Включен -> Используется -> Анализ логов -> Уточнен -> Опубликован группе/всем
```

Для сложных write-skills рекомендуется дополнительный статус:

```text
Требует проверки администратором
```

## Этап 12. Критерии готовности пользовательских skills

Пользовательские skills готовы, если:

- пользователь может создать skill из текстового описания;
- пользователь может включить и выключить skill;
- skill имеет триггеры и человекочитаемый workflow;
- write-skill требует подтверждение перед записью;
- проведение документов запрещено по умолчанию;
- selector учитывает пользовательские skills;
- лог показывает, что был выбран пользовательский skill;
- администратор может посмотреть и отключить любой пользовательский skill.

## Рекомендуемый порядок работ

1. Создать `ИИА_Skills` с реестром в коде.
2. Добавить 3 первых skill: `query-1c-safe`, `metadata-discovery`, `dsl-recovery`.
3. Реализовать selector по триггерам.
4. Встроить skill-блок в `ИИА_Промты.СформироватьПромпт()`.
5. Добавить логирование `[SKILL_SELECTED]`.
6. Прогнать существующие тесты.
7. Добавить базовые тесты selector.
8. Добавить поля contract-ready в структуру skills.
9. Реализовать `ПроверитьDSLПоСкилам()` в режиме `warn`.
10. Добавить регистр `ИИА_Скилы` для пользовательских skills.
11. Сделать форму списка и карточку skill.
12. Реализовать создание skill из текстового описания через агента.
13. Добавить область видимости и права.
14. После накопления логов включать `strict` точечно.

## Главные риски

- Раздувание промпта: нужен жёсткий бюджет skill-блока.
- Конфликт skills: нужен приоритет и ограничение top-N.
- Дублирование правил с системным промптом: часть правил надо постепенно переносить из большого промпта в skills.
- Ложный выбор skill: selector должен логировать score и причину.
- Преждевременный strict: сначала нужен режим `warn`, иначе можно сломать полезные сценарии.
- Пользовательский skill с записью данных: по умолчанию требовать approval и запрещать проведение.
- Слишком свободное описание пользователя: агент должен создавать черновик, а не сразу активный strict-skill.

## Итоговая рекомендация

Делать вариант 2.5 как два независимых слоя:

- `Skill Selector` улучшает мышление модели уже сейчас;
- `Skill Policy` сначала только логируется, а затем становится runtime-контрактом.
- `User Skill Builder` позволяет пользователю описывать бизнес-процедуры без редактирования JSON.

Так агент быстро получает пользу от skills, но архитектура не закрывает дорогу к безопасному contract-first исполнению.
